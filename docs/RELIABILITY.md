Сценарии прогонялись на работающей системе (docker compose: ml + backend + эмулятор), поток — replay архива validate по NDTP.

| Сценарий | Что проверяли | Результат |
|---|---|---|
| Остановка ML-сервиса (`docker stop delay-ml`) | Backend не падает, деградирует | `/health` → `{"status":"ok","ml":"degraded"}`; прогнозы продолжились по правилу (18 точек fallback), дашборд показывает баннер «ML-модуль недоступен» |
| Запуск ML обратно | Автовосстановление | ML поднялся за 5 с; backend сам вернулся на модель (`ml=ok`), без перезапуска |
| Обрыв потока NDTP (остановка replay) | Нет падения, последнее состояние | статус `offline` через 20 с тишины; API отвечает 200; 12 ТС остаются на карте с последней позицией; баннер «Нет связи… последнее известное состояние» |
| Переподключение потока | Восстановление | статус `live`, прогнозы снова выдаются |
| Холодный старт `docker compose restart ml backend` | Предсказуемость | ML готов через 10,7 с, backend — через 13,8 с |
| Эмулятор NDTP, 11 терминалов | Приём | 11 handshake, 0 ошибок CRC |
| Replay суток validate | Пропускная способность | 105 945 пакетов, 0 ошибок CRC, 0 опоздавших точек; ~50–95 пакетов/с |

**Латентность** (живой поток, `/api/stats`, панель «Состояние системы»):
- ML-сервис, батч всех ТС: p50 ≈ 115–135 мс, p95 ≈ 140–185 мс (CatBoost 5+5 моделей + классификатор + квантили + SHAP);
- пересчёт всех ТС за такт прогноза (признаки + ML) ≈ 0,3 с — ориентир жюри «< 1–2 с на поток ТС» выполнен;
- очередей нет: прогноз считается раз в 5 мин времени потока, между тактами только приём пакетов.

**Горизонт:** все прогнозы выдаются за 11–15 мин до события (`/api/analytics` → `lead_min_min/max`); алерты, чьё время наступило, не показываются.

## Калибровка интервала и вероятности (замер 2026-09-27)

Карточка события показывает «Интервал ~80%» и «Вероятность N% · опоздание больше 2 мин». Проверили, насколько им можно верить.

**Онлайн** (`python -m src.realtime.check_all`): сутки validate через NDTP → онлайн-движок, сверка с фактами `labels_test`.
Один день, 13 ТС, **349 точек** (из них 86 опозданий > 2 мин). Интервал и P берутся так же, как на дашборде
(`ops_interval_s`/`ops_p_late`, иначе `interval_s`/`p_late`).

| Что | Все 349 точек | Только события на карточке (жёлтый/красный, 90) |
|---|---|---|
| Факт внутри интервала ~80% | 90,8% (ниже 2,0%, выше 7,2%), медианная ширина 3,9 мин | 78,9% (выше интервала 16,7%) |
| Brier P(опоздание > 2 мин) | 0,071 (константа 0,186) | 0,158 (константа 0,173) |
| AUC | 0,969 | 0,812 |

Надёжность P по корзинам (все точки): 0–0,1 → n=224, средняя P 0,03, опоздало 1%; 0,1–0,3 → n=39, 0,17 / 21%;
0,3–0,5 → n=23, 0,40 / **83%**; 0,5–0,7 → n=28, 0,59 / **82%**; 0,7–1 → n=35, 0,86 / 94%.

**Честные оговорки:**
- Модели P и интервала (`src/train_aux.py --final`) обучены на реальных точках train **и test**, т.е. эти 349 фактов
  модель видела при обучении (признаки онлайн другие — отклонение по GPS, а не из АСУ, — но цели те же). Цифры выше —
  оптимистичная оценка. Офлайн-прогон по `output/features_test.parquet` (353 точки реальных ТС,
  `check_all --offline`) даёт покрытие 99,4% и AUC 1,000 — это запоминание, а не качество, поэтому его не приводим как результат.
- Независимая оценка — out-of-fold CV на 1 494 реальных точках train+test (`python -m src.train_aux`, GroupKFold
  по 2-часовым блокам): AUC 0,863, Brier 0,114 (константа 0,171); P < 0,3 → опоздали 10%, 0,3–0,6 → 47%,
  ≥ 0,6 → 72%; интервал с конформной поправкой 50 с накрывает 80% на отложенной половине блоков.
- Что видно по онлайну: в средних корзинах (P 0,3–0,7) вероятность **занижена** — опаздывает ~82%, а показываем 40–60%.
  Интервал на всех точках шире нужного (91% вместо 80%), а на событиях с карточки — ровно около 80%, но промахи
  несимметричны: факт чаще оказывается **выше** верхней границы (16,7%), т.е. сильные опоздания интервал недооценивает.
- Замер одного дня; на других днях и маршрутах цифры могут отличаться. Модель и пороги по итогам замера не меняли.
