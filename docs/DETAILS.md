## Академическая честность и воспроизведение в потоковом режиме

**Скор с платформы воспроизводится потоковым ML-контуром одной командой:**

```bash
./run.sh python -m src.realtime.stream_submission
# поток: 105945 NDTP-точек … поток vs офлайн: совпало 98.7% точек, max |Δ| 1.30 с
# → output/submission_stream_validate.csv
```

Телеметрия validate кодируется в NDTP-кадры и проходит тот же путь, что на сервере: разбор с проверкой CRC,
затем `OnlineEngine`, затем признаки строго по данным ≤ T, затем модель. Запросы (T, целевая остановка,
`cur_dev_s`) берутся из `points.csv`. Максимальное расхождение 1.3 с: скорость в NDTP передаётся целым числом.
Тот же прогон через настоящий TCP: `docker compose run --rm replay`, затем
`python -m src.realtime.stream_submission --from-jsonl output/realtime_predictions.jsonl`.

**Что мы сознательно НЕ используем** (всё это известные утечки датасета):

| Источник | Почему это утечка | Как гарантируем |
|---|---|---|
| `time_fact_begin` из `train/`/`test/schedule.csv` | там есть факт для всех 151 целевой остановки validate | факт не передаётся в признаки; `tests/test_no_leak.py` меняет факты на ±7 мин → признаки не меняются |
| синтетические ТС `9000xxx` | копии ТС test/validate с их задержками (corr 0.99) | исключены из обучения |
| телеметрия после T | будущее | `tests/test_no_leak.py`: дописываем «будущее» → признаки не меняются |
| время суток + соседние по времени метки того же дня | validate — получасовые куски внутри тех же суток; модель «запомнила бы день» | признак `hour` исключён; валидация — GroupKFold по 2-часовым блокам всех ТС |

Факты расписания используются **только как target** при обучении, как предписывает README организаторов.

## Быстрый старт

Всё запускается в Docker (на хосте нужен только Docker):

```bash
docker compose build                      # образ pulse-route:latest (его использует ./run.sh)
./run.sh python -m src.make_features      # признаки train/test/validate → output/
./run.sh python -m src.train --final      # ансамбль → models/, прогноз validate
./run.sh python -m src.make_submission    # → output/submission.csv (+ проверка формата)
./run.sh python -m pytest -q tests        # анти-утечка, NDTP, паритет онлайн/офлайн
```

`data` — симлинк на распакованный `dataset.zip`.

## Модель

**Признаки** (`src/features.py`, одна функция `features_at` для офлайна и онлайна) строятся только из
планового расписания, телеметрии с `event_time ≤ T` и подсказки `cur_dev_s`. Факты расписания в признаки не
попадают (это проверяет `tests/test_no_leak.py`).

- **Расписание:** сколько остановок/минут до цели, позиция в рейсе, `manual_fill`.
- **GPS-проезды остановок:** задержка на недавно пройденных остановках восстанавливается по треку (медианная
  ошибка 5 с по сравнению с фактом). Проезд засчитывается только когда ТС уже уехало от остановки к моменту T.
- **Прошлые круги того же ТС:** как менялась задержка между «остановкой `cur_dev_s`» и целевой на предыдущих
  проходах маршрута. Это самые сильные признаки после `cur_dev_s`.
- **Движение:** скорости, доля стоянок, расстояние до цели.

**Ансамбль** (`src/train.py`, `src/predict.py`): CatBoost с MAE-лоссом, 2 модели × 5 сидов.
- A — поправка к `cur_dev_s`, обучение на всех целях.
- B — прямая задержка, обучение на целях без `manual_fill`.
- Прогноз = 0.5·A + 0.5·B. Для целей с `manual_fill` (факт внесён диспетчером) прогноз = 0: там задержка
  почти всегда 0.

`manual_fill` — колонка планового расписания, в validate она дана. Но по смыслу она связана с тем, как
заполнялся факт, поэтому признак пограничный. Без неё CV хуже примерно на 2 с.

**Цели с `manual_fill` на дашборде — так же, как в сабмите (прогноз 0).** Проверено на всём дне через онлайн-движок
(`python -m src.realtime.check_all`, факты — `labels_test`): на 38 таких целях официальный факт равен 0 в 95% случаев,
опозданий > 2 мин нет. Альтернативы дали только ложные тревоги: текущее отставание по GPS — MAE 114 с и 12 ложных
предупреждений, модель без правила — MAE 57 с и 7 ложных; правило «0» — MAE 3 с. Детекция проездов по GPS на этих
остановках ненадёжна, поэтому доверяем официальным фактам. Текущее отставание по GPS диспетчер видит отдельно —
в блоке «Сейчас» карточки и на ленте, но тревоги по нему не поднимаются.

## Особенности данных (важно)

1. **Синтетические ТС (`9000xxx`, 74% train) — копии 13 реальных ТС test/validate**, сдвинутые по времени.
   Задержки совпадают с корреляцией 0.99, треки — с точностью около 8 м. Обучение на них даёт фальшивые
   «56 с» на test. **Синтетику не используем.**
2. `validate/traffic.csv` ≡ `test/traffic.csv`, а факты всех целевых остановок validate есть в
   `train/`/`test/schedule.csv`. Факты в признаках не используются.
3. `cur_dev_s` — задержка на последней остановке с **плановым** временем ≤ T (совпадает в 96% случаев).
4. Train, test и validate — одни и те же ТС за одни сутки, перемешанные по времени. Валидация — GroupKFold по
   временным блокам. Признак «час» исключён: он запоминает день.

## Приложение: ML-сервис, Backend, дашборд диспетчера

```bash
docker compose up -d --build             # ml (:8001) + backend (:8080, NDTP :9201)
docker compose --profile synth up -d backend-synth     # второй стенд на синтетике (:8082)
```

**Вход:** своя страница `/login`, учётки из `.env` (`DASH_USER`, `DASH_PASSWORD`, `DASH_EXTRA_USERS`; файл не в
git). Сессия — HMAC-подписанная cookie (HttpOnly, Secure, SameSite=Lax, 12 ч), больше 10 неудачных попыток с одного
IP за 10 минут — отказ; для API-клиентов — Basic auth. Документация кода и Swagger открыты без входа, данные API —
только со входом (в Swagger — кнопка «Authorize»).

- **ML-сервис** (`src/ml_service/app.py`, Swagger `:8001/docs`): stateless инференс — задержка, P(опоздание > 2 мин)
  (AUC 0.86), интервал ~80 % (конформная калибровка), причины (SHAP по факторам); `/v1/model/reload` после
  дообучения.
- **Backend** (`src/backend/app.py`, Swagger `:8080/docs`): приём NDTP, `OnlineEngine`, вызов ML с таймаутом
  (недоступен → прогноз по правилу с флагом `degraded`), онлайн-сверка прогнозов с GPS-проездом, what-if,
  журнал действий диспетчера и отчёт, ленты маршрутов, выбор данных (архив или синтетика), управление
  проигрыванием архива (`/api/replay/*`).
- **Дашборд** (`/`): Leaflet/OpenStreetMap или Яндекс Карты, Chart.js. Три вида:
  - «Карта»: ТС и линии их рейсов в цвете риска, список ТС, карточка события — остановка, «план → прогноз»,
    время выдачи предупреждения, вероятность, интервал, свежесть данных, рекомендации, причина, журнал;
  - «Ленты»: рейс каждого ТС, положение по факту и по графику, очередь событий «Новые → В работе → Завершено»;
  - «Аналитика»: предупреждения во времени, причины, проблемные ТС, точность по фактам, отчёт диспетчеров.
- **Маршруты:** нитка рейса проложена по дорогам через остановки (OSRM, с учётом направления движения), перегоны
  кэшируются в `output/cache`; где роутер даёт крюк — реальный GPS-трек или плановая связь между остановками.

Чего нет в данных, и мы это не выдумываем: номеров маршрутов и типа транспорта (показываем номер ТС), статуса
дверей (эмулятор не шлёт ячейки IRMA/Crown). В реальном датасете по одной машине на маршрут, поэтому несколько
автобусов на маршруте показывает отдельный стенд с синтетикой (`src/synth.py`).

## Real-time контур

```
 эмулятор / терминалы ──NDTP/TCP──▶ server.py ──▶ OnlineEngine ──▶ Predictor ──▶ HTTP API + jsonl
                                    (FrameReader,   (буфер по ТС,     (тот же
                                     CRC, ACK)       T каждые 5 мин)   ансамбль)
```

- `src/realtime/ndtp.py` — кодек NDTP: NPL/NPH, CRC-16/Modbus, ячейки, потоковый разбор с ресинхронизацией.
  Проверен на записанном потоке эмулятора (`tests/emulator_capture.bin`).
- `src/realtime/online.py` — `OnlineEngine`: буфер телеметрии по ТС, момент прогноза T по границам 5 минут
  времени потока, водяной знак для опоздавших точек, выбор цели (первая остановка с планом в (T+10, T+15]).
  - Подсказка `cur_dev_s` приходит из АСУ. В replay она берётся из `points.csv`, если её нет — оценивается
    по GPS.
- `src/realtime/server.py` — asyncio TCP-сервер NDTP (ACK `NPH_RESULT`) + HTTP API:
  `/health`, `/stats`, `/predictions?limit=&tr_id=`.
- `src/realtime/replay.py` — проигрывает архивные треки как NDTP-поток: по соединению на терминал, с
  ускорением времени. Он нужен потому, что эмулятор с `autoGenerate` шлёт случайные точки не по маршрутам.

```bash
docker load -i data/ndtp-telemetry-emulator.tar
docker compose --profile emulator up -d emulator
./scripts/emulator_start.sh 11 1000      # эмулятор → наш NDTP-сервер (проверка приёма)
./scripts/emulator_start.sh stop
curl -u <логин>:<пароль> -X POST localhost:8080/api/replay/start -H 'Content-Type: application/json' \
     -d '{"speed": 30, "start": "2026-01-06 07:00"}'          # архив как поток NDTP, ускоренно
./run.sh python -m src.realtime.check_all    # все ТС за день: поток → прогноз → сверка с фактами
```

Сервисы общаются внутри docker-сети, порты сервисов опубликованы только на 127.0.0.1 (наружу — через reverse
proxy с TLS).

**Проверено (2026-09-25):**
- Эмулятор, 11 терминалов: 11 handshake, 187 кадров, 0 ошибок CRC.
- Replay validate: 30 соединений, 105 945 пакетов, 0 ошибок CRC, 1 645 прогнозов, около 230 мс на пакет
  прогнозов по всем ТС (2 vCPU).
- **Онлайн-прогнозы на 147/151 точке validate совпадают с `submission.csv` до 0.00 с.** В остальных 4 случаях
  две остановки имеют одно плановое время, и организаторы выбрали другую из пары.
- Тест паритета на test (кодек → движок, 349 точек): медиана |Δ| 0.00 с, максимум 8 с.
